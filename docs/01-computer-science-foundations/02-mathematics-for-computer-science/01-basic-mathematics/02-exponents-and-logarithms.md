## Introduction

Two ideas sit at the heart of computing: doubling and halving. Add one bit to a number and it can count twice as high. Double the size of a sorted list and a binary search needs only one more step. Doubling is an **exponent**, and the question "how many doublings?" is a **logarithm**. The two are inverses, and between them they explain why a 64-bit integer holds more than 18 quintillion values, why a billion records can be searched in 30 comparisons, and why some problems can never be solved by simply buying a faster computer.

This lesson covers two syllabus topics, exponents and logarithms. It builds on the percentages of [the previous lesson](01-arithmetic-fractions-percentages-and-ratios.md), where compound growth was repeated multiplication, and it connects directly to the bits and bytes of [Bits, Bytes, Words and Memory Addresses](../../01-computer-fundamentals/03-data-representation/01-bits-bytes-words-and-addresses.md).

## Intuitive understanding

Fold a sheet of paper in half, and again, and again. Each fold doubles the thickness: after $n$ folds the stack is $2^n$ sheets thick. That is an exponent. Now ask the opposite question: how many folds make the stack as tall as the distance to the Moon? Suppose a sheet is 0.1 mm thick and the Moon is about 384,000 km away. After 41 folds the stack would be about 220,000 km tall, and after 42 it would be about 440,000 km, past the Moon. The answer, 42, is a **logarithm**: the number of doublings needed to turn 0.1 mm into 384,000 km. Exponentials start slowly and then explode. Logarithms are the reverse: they grow very slowly, so a huge increase in the input changes the output by only a little.

The paper is only a thought experiment, since real paper cannot be folded that many times, but the arithmetic is exact. The same shapes appear whenever something doubles or halves: bits, tree levels, search steps, compound interest.

## Technical foundations

### Exponents

For a positive whole number $n$, the power $a^n$ means $a$ multiplied by itself $n$ times. Three extensions keep the pattern consistent. Dividing $a^n$ by $a^n$ gives 1, so $a^0 = 1$ for $a \neq 0$. Continuing to divide gives $a^{-n} = 1/a^n$. A fractional exponent is a root: $a^{1/n}$ is the $n$th root of $a$, so $8^{1/3} = 2$. The laws below then hold for all of them.

| Law | Example |
| --- | --- |
| $a^m \cdot a^n = a^{m+n}$ | $2^3 \cdot 2^4 = 2^7$ |
| $a^m / a^n = a^{m-n}$ | $2^7 / 2^4 = 2^3$ |
| $(a^m)^n = a^{mn}$ | $(2^3)^4 = 2^{12}$ |
| $(ab)^n = a^n b^n$ | $(2 \cdot 3)^4 = 2^4 \cdot 3^4$ |
| $a^0 = 1$ and $a^{-n} = 1/a^n$ | $2^{-3} = 1/8$ |
| $a^{1/n}$ is the $n$th root of $a$ | $8^{1/3} = 2$ |

Powers of 2 deserve special attention. A group of $n$ bits can hold $2^n$ different patterns, so $2^8 = 256$ values fit in a byte and $2^{32}$ values in a 32-bit integer. A few are worth remembering: $2^{10} = 1024$ is close to a thousand, and the kibibyte (KiB) is exactly $2^{10}$ bytes; $2^{20}$ is about a million; and $2^{32}$ is about 4.3 billion.

### Exponential growth

Something grows **exponentially** when it is multiplied by a fixed factor in each step: $y = c \cdot b^n$. Compound interest and doubling are examples. Compare that with **polynomial** growth, where the exponent is fixed and the base grows, as in $n^2$. At $n = 10$ the exponential $2^n$ (1,024) and the cube $n^3$ (1,000) are almost equal. At $n = 20$ the exponential is 131 times larger, at $n = 30$ about 40,000 times larger, and at $n = 40$ about 17 million times larger. In the end any exponential overtakes any polynomial.

That is why algorithms are sorted by their growth rate. An algorithm that needs $2^n$ steps for an input of size $n$ takes about 18 minutes at $n = 40$ on the assumed billion-step-a-second machine, 13 days at $n = 50$, 36 years at $n = 60$ and about 38 million years at $n = 80$. A machine a thousand times faster would only push each of those limits up by about ten, as exercise 8 shows. This is why problems with only exponential-time algorithms are treated as practically unsolvable for large inputs, and why a central question of computer science is which problems have fast algorithms.

### Fast exponentiation

Computing $a^n$ by multiplying $n$ times is slow when $n$ is large. Writing $n$ in binary gives a much faster way. For example $13 = 1101_2$, so $a^{13} = a^8 \cdot a^4 \cdot a^1$. The powers $a^1, a^2, a^4, a^8$ come from repeated squaring, and a power is multiplied into the result exactly when the matching binary digit is 1. This method is called **square-and-multiply**, and it needs about $\log_2 n$ squarings plus at most one extra multiplication per binary digit.

<!-- run:python -->
```python
def power_slow(base, n):
    result, multiplications = 1, 0
    for _ in range(n):
        result *= base
        multiplications += 1
    return result, multiplications

def power_fast(base, n):
    """Square-and-multiply: use the binary digits of n."""
    result, multiplications = 1, 0
    while n > 0:
        if n & 1:                       # this binary digit of n is 1
            result *= base
            multiplications += 1
        base *= base                    # square: base^1, base^2, base^4, base^8, ...
        multiplications += 1
        n >>= 1
    return result, multiplications

for n in (10, 100, 1000):
    slow, fast = power_slow(3, n), power_fast(3, n)
    print(f"3^{n}: same answer {slow[0] == fast[0]}; multiplications slow {slow[1]}, fast {fast[1]}")

# Modular exponentiation: pow(a, n, m) never builds the huge number
print(pow(7, 128, 13), 7**128 % 13, pow(7, 10**18, 13))
```

Public-key cryptography depends on this: its operations are modular exponentiations with numbers hundreds of digits long.

### Logarithms

The **logarithm** undoes exponentiation. For a base $b > 0$ with $b \neq 1$ and a number $x > 0$, $\log_b x = y$ means $b^y = x$. So $\log_2 8 = 3$ because $2^3 = 8$, and $\log_{10} 1000 = 3$ because $10^3 = 1000$. Three bases are common: base 2 in computing, base 10 for orders of magnitude, and base $e \approx 2.71828$, written $\ln$, in calculus and science. In algorithm analysis, "$\log n$" usually means base 2, but the base rarely matters for growth rates, because changing it only multiplies by a constant.

```mermaid
flowchart LR
    X["x"] -->|"raise b to the power x"| Y["y = b to the power x"]
    Y -->|"take the logarithm to base b"| X
```

*Reading the diagram:* the two operations undo each other, like squaring and taking a square root. Because exponentiation turns addition into multiplication ($b^m \cdot b^n = b^{m+n}$), the logarithm turns multiplication back into addition, which is the first rule below.

| Law | Example |
| --- | --- |
| $\log_b(xy) = \log_b x + \log_b y$ | $\log_2(8 \cdot 4) = 3 + 2 = 5$ |
| $\log_b(x/y) = \log_b x - \log_b y$ | $\log_2(8/4) = 3 - 2 = 1$ |
| $\log_b(x^k) = k \log_b x$ | $\log_2(8^2) = 2 \times 3 = 6$ |
| $\log_b x = \log_c x / \log_c b$ | $\log_2 1000 = \ln 1000 / \ln 2 \approx 9.9658$ |
| $\log_b 1 = 0$ and $\log_b b = 1$ | $\log_{10} 1 = 0$ |

The fourth law, the **change of base**, lets any calculator or library that has natural logarithms compute a logarithm in any base.

### Why logarithms appear everywhere in computing

- **Bits and digits.** A positive whole number $n$ needs $\lfloor \log_2 n \rfloor + 1$ bits, where $\lfloor \cdot \rfloor$ rounds down, and $\lfloor \log_{10} n \rfloor + 1$ decimal digits. Numbering $n$ distinct items from 0 to $n - 1$ needs $\lceil \log_2 n \rceil$ bits, where $\lceil \cdot \rceil$ rounds up.
- **Halving.** Each step of a binary search discards half of what is left, so searching $n$ sorted items takes at most $\lfloor \log_2 n \rfloor + 1$ comparisons. The same count gives the height of a balanced binary tree.
- **Information.** Choosing among $N$ equally likely options takes $\log_2 N$ bits of information. Information theory builds on this idea.
- **Scales.** When values span many orders of magnitude, such as file sizes or sound levels, a logarithmic scale shows them on one chart.

```mermaid

    A["1,000,000 items"] -->|"halve"| B["500,000"] -->|"halve"| C["250,000"] -->|"halve"| D["and so on"] -->|"halve"| E["1 item"]
```

*Reading the diagram:* a million items shrink to one after about 20 halvings. That count is $\log_2 1{,}000{,}000 \approx 19.93$, and the program below counts it exactly.

<!-- run:python -->
```python
import math

# How many bits does a number need?  floor(log2 n) + 1, which is exactly n.bit_length()
for n in (1, 2, 255, 256, 1_000_000):
    print(f"n = {n:>9,}: bit_length {n.bit_length():>2}, floor(log2 n) + 1 = {math.floor(math.log2(n)) + 1:>2}")

# Digits of a number in base 10: floor(log10 n) + 1
print(len(str(2**100)), math.floor(100 * math.log10(2)) + 1)

# Logarithm rules, checked numerically (rounded, because floating-point logs are approximate)
x, y = 1000, 64
print(round(math.log2(x * y), 6), round(math.log2(x) + math.log2(y), 6))
print(round(math.log2(x), 4), round(math.log(x) / math.log(2), 4))          # change of base
print(round(math.log10(2) + math.log10(5), 10))                            # log 2 + log 5 = log 10 = 1

# A pitfall: floating-point log2 of a huge integer rounds up to the next integer
big = 2**1000 - 1
print("exact floor(log2):", big.bit_length() - 1, "| float version:", math.floor(math.log2(big)))

# Worst-case number of comparisons in a binary search of n sorted items
def comparisons_worst_case(n):
    low, high, steps = 0, n - 1, 0
    while low <= high:                  # always look in the larger half to find the worst case
        mid = (low + high) // 2
        steps += 1
        left, right = mid - low, high - mid
        if left >= right:
            high = mid - 1
        else:
            low = mid + 1
    return steps

for n in (10, 1000, 1_000_000, 1_000_000_000):
    print(f"n = {n:>13,}: {comparisons_worst_case(n):>2} comparisons, floor(log2 n) + 1 = {n.bit_length()}")
```

## Real-world applications

- **Searching and indexing.** Binary search and balanced trees take about $\log_2 n$ steps. A database index tree whose nodes each have about 100 children reaches a billion records in about 5 levels, because $\log_{100} 10^9 = 4.5$ (a round figure for illustration, since real fan-outs vary).
- **Sizes and addresses.** $n$ bits can address $2^n$ locations, so 32 bits address $2^{32}$ bytes, which is 4 GiB. See [Bits, Bytes, Words and Memory Addresses](../../01-computer-fundamentals/03-data-representation/01-bits-bytes-words-and-addresses.md).
- **Cryptography.** Public-key schemes rely on modular exponentiation with very large numbers, and the difficulty of reversing it, the discrete logarithm, protects their keys. Key sizes are quoted in bits.
- **Information and compression.** The number of bits needed to distinguish $N$ equally likely messages is $\log_2 N$, which sets the limit that compression approaches.
- **Floating point.** An IEEE 754 number is a significand times a power of two, so the exponent field of a float is an exponent in exactly this sense. See [Floating Point and IEEE 754](../../01-computer-fundamentals/02-number-systems/05-floating-point-and-ieee-754.md).
- **Growth and finance.** Compound interest multiplies by $(1 + r)$ every period, and the time to double is a logarithm. A common shortcut, the rule of 72, estimates it as 72 divided by the percentage rate.
- **Scales.** Sound level in decibels is 10 times the base-10 logarithm of a power ratio, which squeezes an enormous range into a small one.

## Comparisons and trade-offs

There are three ways to compute $\lfloor \log_2 n \rfloor$ in Python, and they are not equally trustworthy.

| Method | Exact? | Works for | Comment |
| --- | --- | --- | --- |
| `n.bit_length() - 1` | Yes | Positive integers of any size | The right choice for integers |
| `math.floor(math.log2(n))` | No | Any positive number | Can be wrong for large integers just below a power of two |
| `math.floor(math.log(n, 2))` | No | Any positive number | Worse still: it divides two approximate logarithms |

Exact integer methods are better when the input is a whole number, and floating-point logarithms are right when the input is a measurement that is already approximate.

## Advanced concepts

- **The discrete logarithm.** In modular arithmetic, computing $b^x \bmod m$ is fast by square-and-multiply, but recovering $x$ from the result is believed to be very hard when $m$ is large. This one-way behaviour underlies the Diffie–Hellman key exchange.
- **Complex exponentials.** Euler's formula $e^{ix} = \cos x + i \sin x$ ties exponentials to rotation and underlies the Fourier transform used in signal processing.
- **Accurate functions for tiny numbers.** `math.log1p(x)` and `math.expm1(x)` compute $\log(1 + x)$ and $e^x - 1$ accurately when $x$ is very small, where the direct formulas lose digits.
- **Log-probabilities.** The product of many small probabilities underflows to 0 in floating point. Adding their logarithms instead keeps the information, which is why machine-learning code works with log-likelihoods.

## Common mistakes

> **Common mistake:** *Treating a sum like a product.* $(a + b)^2$ is not $a^2 + b^2$, and $\log(a + b)$ is not $\log a + \log b$. The laws apply to products and powers only.

- **Writing `^` for a power.** In Python and C, `^` is bitwise XOR. Use `**` in Python and `pow()` in C.
- **Taking the logarithm of zero or a negative number.** It is undefined for real numbers, and `math.log(0)` raises an error.
- **Mixing bases.** A formula derived with $\ln$ gives the wrong number if you plug in a base-2 logarithm. Use the change-of-base law.
- **Mixing up bits for a value and bits for a count.** The value $n$ needs $\lfloor \log_2 n \rfloor + 1$ bits, but numbering $n$ items from 0 needs $\lceil \log_2 n \rceil$ bits, which is `(n - 1).bit_length()`.
- **Using floats for huge exact powers.** `2.0 ** 1024` overflows, while the integer `2 ** 1024` is exact.
- **Trusting float logarithms for integer answers.** See the $2^{1000} - 1$ example above.

import math

def multiplications(n):
    """Multiplications in square-and-multiply: one squaring per binary digit, one more per 1-digit."""
    count = 0
    while n > 0:
        count += (n & 1) + 1
        n >>= 1
    return count

## Interview and practical questions

**Why is binary search $O(\log n)$?** Each comparison discards half of the remaining items, so the number of items left after $k$ comparisons is about $n / 2^k$, and the search ends when that reaches 1, after about $\log_2 n$ steps.

**How many bits does it take to represent the integer $n$?** $\lfloor \log_2 n \rfloor + 1$ for $n \ge 1$, which is `n.bit_length()` in Python.

**How can you compute $a^n$ with far fewer than $n$ multiplications?** By square-and-multiply: square repeatedly and multiply the result in wherever the binary digit of $n$ is 1. It takes at most about $2 \log_2 n$ multiplications.

**What does it mean in practice for an algorithm to take $O(2^n)$ time?** That its running time doubles with every added item of input, so it is usable only for small inputs. Waiting for faster computers hardly helps.

**Why is `pow(a, n, m)` better than `a ** n % m`?** It reduces modulo $m$ after every multiplication, so the intermediate numbers stay small, whereas `a ** n` first builds a number with an enormous number of digits.
